Slide 1 / 5 — The job

Cleaning up a tangled CRM, one cluster at a time.

Our CRM has thousands of partner brands, their locations, and the deals that link them. Over time they get duplicated, mis‑parented, and drift out of sync with our internal systems and the live web.

The unit of work is a cluster: one brand and everything attached to it. Find the mess, propose the fix, write it back. Sounds simple. It isn't.

      Slide 3 / 5 — The obvious objection

      Why not just build this in n8n?

      Honest answer: most of the time, you should. n8n is the obvious place for this kind of work — visual workflows, queues, retries, wait‑and‑resume, all out of the box. We use it elsewhere. The question is where it stops being a good fit.

      n8n wins when…

      • The flow is "fetch X, classify with one LLM call, write back" — 1:1 nodes you already have
      • You want non‑engineers editing prompts in a browser
      • You want visible run history and node outputs in a browser
      • You need wait‑and‑resume durability for days, not minutes
      • The team is bigger than one person
      • You don't want to maintain a runtime

      It hits a wall when…

      • Multi‑turn agent sessions need pause / resume / mid‑run operator chat
      • Pipelines need state checkpoints, replay‑from‑step, supervisor fan‑out
      • You want prompt cache hits across sibling LLM calls (real $)
      • You want unit tests and fixture‑based integration tests on the logic
      • The flow grows past ~100 nodes — visual programming stops scaling
      • You need the same prompt template forked 5 ways without copy‑paste rot

      The complexity is in the problem. n8n makes it visible; code makes it composable. Pick by which side of that trade you actually need.

      Slide 4 / 5 — The breakthrough

      Stop asking the model for prose. Ask for a schema.

      The architect step — the part that proposes the fix — used to emit a paragraph of recommendations. We replaced that with validated JSON:

      type Op =
  | { verb: "consolidate"; from: Id; into: Id; reason: string }
  | { verb: "set_parent";  parent: Id; child: Id; reason: string }
  | { verb: "create_rl";   address: string; company: Id; reason: string }
  | { verb: "archive";     id: Id; reason: string }
  | ...

interface StructureOutput {
  before: TreeSnapshot;
  after:  TreeSnapshot;
  ops:    Op[];
}

      TypeScript deterministically renders the markdown the next stage reads. Same shape every run, regardless of how the model phrased itself. This is what moves the dial from the failed April position to the working "Today" position.

      Slide 5 / 5 — Today

      Typed plan in. Agent executes turn by turn.

      The fix step is now an agent. It runs the same bash scripts the March code ran — but it calls them as tools, reads the live system between writes, and pauses to ask a human when reality doesn't match the plan.

      March

      • Code freezes a plan from stale data
      • Bash executes blind
      • One shot, no adaptation

      Today

      • Typed plan in, validated
      • Agent reads live state between writes
      • Pauses to ask when surprised

      The question isn't "is the agent in charge?" It's what shape is the contract between the typed plan and the live tools? Get that right and the agent is reliable. Get it wrong and no model size will save you.
